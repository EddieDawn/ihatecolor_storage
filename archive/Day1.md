# Day 1 — Wedding Snap Portfolio

> 작업일: 2026-08-14  
> 프로젝트 목적: 웨딩 스냅 사진작가의 포트폴리오 사이트 제작

## 1. 오늘 한 일

### 프로젝트 방향 논의

- 사진 포트폴리오에 필요한 기술 스택과 배경지식을 검토했다.
- 콘텐츠 중심의 정적 사이트에 적합한 Astro, TypeScript, 기본 CSS 구성을 우선 추천했다.
- CMS는 사진작가가 직접 콘텐츠를 자주 수정해야 할 때 추가하기로 하고, 초기 개발에서는 미루기로 했다.
- 사진 사이트에서 중요한 이미지 최적화, 반응형 이미지, 접근성, 저작권과 EXIF 관리도 함께 검토했다.

### 디자인 레퍼런스 분석

다음 두 사이트를 디자인 레퍼런스로 분석했다.

- House Noma — `https://www.housenoma.com/nu-noma`
  - 넓은 여백
  - 미술관의 작품 설명처럼 사진 주변에 배치된 텍스트
  - 서로 다른 이미지 크기
  - 첫 화면의 세로 이미지와 느린 움직임
- Studio IVE — `https://www.studioive.co/`
  - 절제된 내비게이션과 균형 잡힌 구성
  - 작은 글자와 넓은 자간
  - Journal 페이지의 3열 카드
  - 기본 흑백 이미지가 호버 시 컬러로 바뀌는 효과

House Noma의 첫 화면 움직임은 복잡한 실시간 효과가 아니라 약 18.5초짜리 MP4 자동 재생 방식임을 확인했다. 실제 사이트에서는 영상 대신 가벼운 이미지 확대·이동 애니메이션으로 시작하는 것이 현실적이라고 판단했다.

### Prototype B 제작

경로: [`../prototype-b/index.html`](../prototype-b/index.html)

Monochrome Journal 방식의 프로토타입을 제작했다.

- 데스크톱 3열 사진 카드
- 넓은 좌우 여백과 중앙 워드마크
- 기본 흑백, 호버·키보드 포커스 시 컬러 전환
- 카테고리 필터
- 전체 화면 사진 상세 보기
- 이전·다음 사진 이동
- 작품명, 장소, 연도 캡션
- 프로젝트 내부 이미지 사용으로 외부 서버 의존성 제거

모바일 구현도 일부 작성했지만, 최종 모바일 디자인 검토는 이후로 미뤘다. 현재 승인된 핵심 기준은 데스크톱 화면이다.

### Prototype C 제작

경로: [`../prototype-c/index.html`](../prototype-c/index.html)

Editorial Hybrid 방식의 데스크톱 프로토타입을 제작했다.

- 화면 높이를 채우는 어두운 랜딩 Hero
- 대표 사진의 느린 공개 및 축소 애니메이션
- 12열 기반의 비대칭 사진 에세이
- 사진마다 다른 크기, 비율과 상하 간격
- 미술관 라벨 같은 작품 캡션
- 중간 인용문과 편집형 텍스트 구간
- 하단의 3열 흑백 저널
- 전체 화면 사진 상세 보기와 이전·다음 이동

1440×900에서 다음 항목을 실제로 검증했다.

- 가로 넘침 없음
- Hero가 화면 높이를 정확히 채움
- 비대칭 사진 배치 정상
- 저널 3열 정상
- 흑백에서 컬러로 바뀌는 호버 정상
- 상세 보기와 이전·다음 이동 정상
- 깨진 이미지와 콘솔 오류 없음

### 이미지 자산 정리

- 사용자가 `content/`에 넣은 사진 5장을 사용했다.
- 프로토타입 제작 중 생성된 임시 다큐멘터리 사진도 함께 사용했다.
- 워터마크처럼 보이는 흔적이 있던 생성 이미지 1장은 제외했다.
- 큰 PNG는 웹용 JPEG로 변환해 파일 크기를 줄였다.
- B와 C 모두 각자의 `assets/` 폴더에 필요한 이미지를 포함한다.

### 디자인 규칙 문서화

- 폰트 스택, 크기, 자간, 행간과 두께
- 좌우 여백
- Hero와 섹션 패딩
- 12열 에세이의 사진 위치와 오프셋
- 3열 카드의 크기와 간격
- 이미지 비율과 캡션
- Hero, 스크롤 공개, 흑백 호버 애니메이션
- 페이지네이션 원칙
- 접근성과 품질 기준
- 금지되는 디자인 변화
- 변경 승인 절차

## 2. 오늘 확정한 결론

### 최종 사이트 구조

사이트는 두 가지 프로토타입을 결합한다.

1. 랜딩 페이지는 **Prototype C 방식**을 사용한다.
2. 메인 메뉴의 `Photos`와 같은 항목을 누르면 **Prototype B 방식의 사진 목록**으로 이동한다.
3. 사진 목록은 데스크톱에서 3열 카드를 사용한다.
4. 사진 목록이 많아지면 무한 스크롤이 아닌 명시적인 페이지네이션을 적용한다.

### 디자인 기준

- Prototype C는 랜딩 페이지의 시각적 기준이다.
- Prototype B는 사진 목록 페이지의 시각적 기준이다.
- 두 프로토타입은 비교 기준이므로 별도 요청 없이 수정하지 않는다.
- 디자인 규칙의 단일 기준 문서는 `docs/DESIGN_SYSTEM.md`다.
- 디자인 시스템을 바꿀 필요가 생기면 구현 전에 사용자에게 문서 수정 여부를 묻는다.

### 폰트

현재 프로토타입은 다음과 같은 시스템 폰트 스택을 사용한다.

```css
font-family:
  "Helvetica Neue",
  Helvetica,
  Arial,
  "Pretendard",
  "Apple SD Gothic Neo",
  sans-serif;
```

따라서 운영체제에 따라 실제 사용되는 폰트가 조금 달라질 수 있다.

추후 웹 임베딩이 허용된 폰트 파일을 프로젝트에 포함하고 `@font-face`로 지정하면 데스크톱과 모바일에서 같은 폰트를 사용할 수 있다. 다만 운영체제와 브라우저의 렌더링 차이 때문에 픽셀 단위로 완전히 동일하지는 않다.

폰트를 선택할 때 반드시 확인할 사항:

- 웹폰트 사용 허용 여부
- 프로젝트와 함께 파일을 배포할 수 있는지
- 상업적 사용 허용 여부
- 필요한 한글·영문 글리프 제공 여부
- 사용할 굵기별 폰트 파일 제공 여부
- 가능하면 `WOFF2` 형식 제공 여부

## 3. 아직 결정하지 않은 것

- 사진작가의 실제 이름과 워드마크

- 랜딩에서 사진 목록으로 이동할 실제 URL

- 카테고리 필터를 실제 사이트에서도 사용할지
- 실제 웨딩 사진과 사진별 캡션
- 작가 소개, 경력과 연락처
- 한글과 영어를 병기하는 방식
- 실제 사용할 웹폰트와 라이선스
- 모바일 랜딩과 모바일 사진 목록 디자인
- 최종 프레임워크와 배포 환경

## 5. 작업을 이어갈 때 지켜야 할 절차

1. 루트의 `AGENTS.md`를 읽는다.
2. `docs/DESIGN_SYSTEM.md`를 처음부터 끝까지 읽는다.
3. Prototype C와 B를 시각적 비교 기준으로 사용한다.
4. 디자인 시스템과 다른 변경이 필요하면 먼저 사용자에게 묻는다.
5. 전역 디자인 변경이 승인되면 문서를 먼저 수정한다.
6. 구현 후 1440×900에서 디자인 체크리스트를 검증한다.

## 6. 프로토타입 실행 방법

프로젝트 루트에서 다음 명령 중 하나를 실행한다.

```powershell
# Prototype B
python -m http.server 4173 --bind 127.0.0.1 --directory prototype-b

# Prototype C
python -m http.server 4174 --bind 127.0.0.1 --directory prototype-c
```

그다음 브라우저에서 다음 주소를 연다.

- Prototype B: `http://127.0.0.1:4173/`
- Prototype C: `http://127.0.0.1:4174/`

`index.html`을 직접 열 수도 있지만, 브라우저의 로컬 파일 제한을 피하기 위해 로컬 서버 방식을 권장한다.
