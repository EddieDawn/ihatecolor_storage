# Day 2 — 기획 보완과 기술 스택 확정

> 작업일: 2026-08-18  
> 프로젝트: 웨딩 스냅 사진작가 포트폴리오 사이트

## 1. 오늘 논의한 개발 방식

기존의 `기획 → 디자인 → 프론트엔드 → 백엔드` 순서를 현재 프로젝트에 그대로 적용할지 검토했다.

현재 프로젝트는 시각 프로토타입이 먼저 구체화됐지만 실제 브랜드, 콘텐츠 운영 방식, URL, CMS와 배포 환경 등 일부 핵심 기획이 남아 있다. 따라서 완전한 직렬형 개발보다 다음 방식이 적합하다고 판단했다.

1. 필요한 기획 결정을 먼저 닫는다.
2. 디자인과 기술 구조를 함께 검증한다.
3. 실제 데이터 계약에 가까운 모크 콘텐츠로 하나의 완성된 사용자 흐름을 구현한다.
4. 필요한 경우에만 CMS 또는 백엔드 기능을 추가한다.

현재 사이트에는 별도의 범용 백엔드가 반드시 필요한 것은 아니다. 콘텐츠 관리는 관리형 CMS에 맡기고 사이트는 정적 생성을 중심으로 구성할 수 있다.

## 2. Notion의 출시 전 작업 검토

Notion의 `출시 전` Phase에 포함된 작업을 확인했다.

- 출시용 실제 웨딩 포트폴리오 사진 선별
- 초상권·사용 허가·EXIF 공개 범위 점검
- 작품 캡션과 메타데이터 작성
- 배포 환경과 도메인 확정
- 검색 노출과 공유 메타데이터 설정

`출시 전`은 작업의 완료 시점을 뜻하며 모든 항목이 지금 가장 먼저 수행되어야 한다는 뜻은 아니다. 콘텐츠 선별과 권리 확인은 구현 입력에 가까운 반면, SEO와 공유 메타데이터는 URL과 콘텐츠가 정해진 뒤 처리할 수 있다.

이후 운영 전제가 수정되면서 실제 웨딩 사진 선별은 당장 진행하지 않고, 로컬 모크 콘텐츠를 먼저 사용하기로 했다.

## 3. 콘텐츠 운영 주체

최종 사이트에서 사진을 업로드하고 게시 여부를 결정하는 사람은 개발자가 아니라 사진작가인 친구다.

- 초상권과 사진 사용 허가 여부는 사진작가가 판단한다.
- 사이트는 그 판단을 대신하지 않는다.
- 필요하면 CMS에 비공개 게시 승인 필드를 두어 실수로 미승인 사진을 공개하는 일을 방지한다.
- 별도의 관리자 화면을 직접 개발하기보다 관리형 CMS의 편집 화면을 사용한다.

## 4. EXIF 정책

EXIF는 사진 파일에 포함될 수 있는 촬영 메타데이터다. 촬영 날짜와 시간, 카메라와 렌즈, 셔터 속도, 조리개, ISO, 방향, GPS 위치 등이 포함될 수 있다.

일반적인 포트폴리오 공개 이미지에서는 불필요한 EXIF를 제거하는 방향을 선택했다.

- 원본은 CMS 정책에 따라 보관할 수 있다.
- 공개 웹 이미지에서는 GPS, 정확한 촬영 시각과 기기 정보 등을 제거한다.
- 공개가 필요한 저작권 정보는 EXIF에 의존하지 않고 별도의 콘텐츠 필드로 관리한다.
- 최종 이미지 파이프라인에서 EXIF가 실제로 제거되는지 출시 전에 검증한다.

## 5. 모킹 전략

실제 웨딩 사진과 CMS가 준비되기 전에는 모킹을 사용한다.

현재 단계에서 필요한 것은 API 모킹보다 콘텐츠 모킹이다. 실제 콘텐츠와 동일한 필드 구조를 가진 로컬 데이터와 모크 이미지를 사용해 화면과 데이터 흐름을 구현한다.

모크 데이터에는 정상적인 사례만 넣지 않는다.

- 세로형, 가로형, 정사각형과 극단적인 비율의 이미지
- 짧은 제목과 긴 제목
- 선택 메타데이터가 없는 사진
- 빈 목록과 사진 한 장만 있는 목록
- 페이지네이션 경계보다 많은 사진
- `draft`와 `published` 상태

실제 네트워크 API가 생기기 전에는 MSW를 도입하지 않는다. CMS API 연동이나 오류 응답 테스트가 필요해질 때 추가한다.

## 6. 확정한 기술 스택

다음 기술 선택을 확정했다.

| 영역 | 선택 |
|---|---|
| 웹 프레임워크 | Astro |
| 언어 | TypeScript strict mode |
| 패키지 매니저 | pnpm |
| Node.js | 24.19.0 LTS |
| 초기 콘텐츠 소스 | 로컬 Astro Content Collection |
| 최종 콘텐츠 소스 | 관리형 Sanity CMS |
| 개발환경 | Docker |

Astro와 pnpm의 정확한 패키지 버전은 프로젝트를 초기화할 때 안정 버전을 확인한 뒤 lockfile과 Docker 설정에 고정하기로 했다. 릴리스 후보와 실험 버전은 명시적인 필요가 없다면 사용하지 않는다.

## 7. 콘텐츠 데이터 구조

초기 버전에서는 사진 한 장을 하나의 독립된 작품으로 취급한다.

### 필수 필드

- `id`
- `slug`
- `image`
- `title`
- `altText`
- `status`
- `sortOrder`

### 선택 필드

- `caption`
- `location`
- `shotAt`
- `category`
- `albumId`

향후에는 `Album 1 : N Photo` 구조를 추가할 수 있다. 사진의 `id`와 `/photos/[slug]` URL은 앨범에 종속시키지 않아 기존 작품 URL을 유지한다. 기존 독립 사진은 앨범이 없는 상태로 두거나 `Singles`와 같은 기본 앨범으로 이전할 수 있다.

## 8. 로컬 콘텐츠 구조

초기 모크 콘텐츠는 사진 한 장당 데이터 파일과 이미지 한 개를 함께 두는 Astro Content Collection으로 구성하기로 했다.

```text
src/data/photos/
  mock-photo-01/
    index.md
    image.jpg
  mock-photo-02/
    index.md
    image.jpg
```

이미지를 `src/` 아래에 두어 Astro의 이미지 크기 추론과 최적화를 사용할 수 있게 한다. 화면 컴포넌트는 로컬 데이터나 Sanity SDK에 직접 결합하지 않고, 공통 `Photo` 모델로 정규화된 데이터를 받는다.

## 9. Sanity 전환 방향

최종 콘텐츠 소스로 관리형 Sanity CMS를 사용하기로 했다.

- 사진작가가 Studio에 로그인해 사진을 업로드한다.
- 제목, 캡션, 공개 상태와 표시 순서를 관리한다.
- 초기 로컬 데이터와 Sanity 데이터를 동일한 애플리케이션 모델로 변환한다.
- 화면 컴포넌트에서 Sanity SDK를 직접 호출하지 않는다.
- 별도의 커스텀 관리자 화면과 범용 백엔드는 초기 범위에서 제외한다.

## 10. Docker 개발환경 방향

회사와 집에서 같은 개발환경을 사용하기 위해 Docker를 먼저 구성하기로 했다. 단, Docker만으로 소스 코드와 비밀값이 동기화되는 것은 아니므로 Git과 환경변수 관리가 함께 필요하다.

- Node.js `24.19.0` 고정
- pnpm 안정 버전 고정
- Git에 `pnpm-lock.yaml` 포함
- Astro 개발 서버 포트 노출
- 소스 bind mount
- `node_modules`와 pnpm 캐시 분리
- `.env.example` 제공
- Sanity 토큰과 비밀값은 Git에서 제외

관리형 Sanity를 사용하므로 초기 Docker 환경에는 로컬 데이터베이스나 CMS 서버를 추가하지 않는다. 처음에는 Astro 애플리케이션 하나만 컨테이너로 실행한다.

## 15. Docker 개발환경 구성

확정된 기술 스택을 기준으로 실제 Astro와 Docker 개발 기반을 구성했다.

- Node.js `24.19.0`
- pnpm `11.22.0`
- Astro `7.2.2`
- TypeScript `6.0.3` strict mode
- `@astrojs/check` `0.9.10`

TypeScript 최신 메이저 버전은 `@astrojs/check`의 peer dependency 범위를 벗어나 사용하지 않았다. 지원 범위 내 최신 안정 버전인 `6.0.3`으로 고정했다.

pnpm의 의존성 설치 스크립트 보호 기능이 `esbuild`의 postinstall을 차단하는 것을 확인했다. 모든 스크립트를 허용하지 않고 `pnpm-workspace.yaml`의 `allowBuilds`에 `esbuild`만 명시적으로 허용했다.

다음 파일을 추가했다.

- `package.json`
- `pnpm-lock.yaml`
- `pnpm-workspace.yaml`
- `astro.config.mjs`
- `tsconfig.json`
- `Dockerfile`
- `compose.yaml`
- `.dockerignore`
- `.gitignore`
- `.env.example`
- `src/env.d.ts`
- `src/pages/index.astro`
- `src/pages/health.ts`
- `docs/DEVELOPMENT.md`

제품 UI는 아직 구현하지 않았다. 루트 경로에는 빈 자리표시자만 두고 `/health`에서 개발환경 상태를 텍스트로 반환한다.

검증 결과:

- Docker 이미지 빌드 성공
- `pnpm install --frozen-lockfile` 성공
- `astro check`: 오류 0, 경고 0, 힌트 0
- `astro build`: 정적 페이지 빌드 성공
- Compose 서비스 상태: `healthy`
- `http://localhost:4321/health`: HTTP 200 및 정상 메시지 반환
